\section{Protocols}
\label{sec:protocols}

\subsection{Architecture and protocol termination}

DAQ configuration is integrated into the external OPC UA server. DAQ supplies
the configuration request through this server, which contains the component
that translates the versioned DAQ configuration contract into the DAPHNE
Protobuf/ZeroMQ exchange. Ignition connects to the same OPC UA server for the
SC interface. The server is the common routine protocol endpoint for the
DAPHNE configuration path. \textbf{Hermes remains separate}: its DAQ client
uses IPBus over UDP directly to the board-side Hermes service.

For the DAPHNE path, the software chain is:
\begin{quote}
DAPHNE internal service $\longleftrightarrow$ ZeroMQ server
$\longleftrightarrow$ Protobuf client in the external OPC UA server
$\longleftrightarrow$ OPC UA $\longleftrightarrow$ Ignition / DAQ client.
\end{quote}
The Protobuf client is an application component. Protobuf encodes the messages;
ZeroMQ frames and routes them over TCP. Neither is a physical interface.

\subsection{OPC UA and the integrated DAQ configuration component}

The external server terminates OPC UA and owns the translation between its
versioned service contract and the DAPHNE application protocol. The DAQ
configuration definitions remain tied to the selected \code{daphnemodules}
release [R3]; the server incorporates the configuration implementation and
its compatible Protobuf client. A second independent configuration client
shall not bypass this server in routine operation.

The transport baseline for the OPC UA boundary is UA TCP with the binary
mapping [R8]. The deployment shall specify the complete endpoint URL,
application identity, certificate trust, user/application authentication,
security policy and message-security mode. These choices apply to the
Ignition and DAQ connections to the external server. They do not imply that
OPC UA terminates on DAPHNE or encrypts a subsequent ZeroMQ connection.

An OPC UA session or accepted method invocation is not, by itself, evidence
that a DAPHNE operation finished. The server contract shall distinguish
request admission, dispatch, completion and failure, with an operation
identifier and a bounded result path for long operations. Queue limits,
timeouts, cancellation and reconnect behavior shall be specified before
integration. A retry after a lost reply shall not silently repeat a
non-idempotent operation.

OPC UA service requests, monitored-item subscriptions and method calls have
different exchange patterns. Their use and supported profiles shall be
documented in the server's released protocol description. Selecting OPC UA
does not select a ZeroMQ PUB/SUB backend. The implementation shall explicitly
state which backend work is requested and which work runs periodically.

\subsection{DAPHNE: Protobuf over ZeroMQ over TCP}

The audited board service uses a ZeroMQ ROUTER socket and the DAQ reference
client uses a DEALER socket [R3, R4]. This is a request/reply application
protocol implemented with ROUTER/DEALER. It shall not be documented as a
ZeroMQ REQ/REP or PUB/SUB endpoint. The integrated OPC UA server shall use the
compatible client framing.

The network payload is a serialized \code{ControlEnvelopeV2} containing the
typed Protobuf request or response. The board implementation accepts envelope
version 2 and request direction, dispatches the message type, and returns a
correlated response. It preserves the task identifier, correlates replies to
the request message identifier, and supports multiple replies for chunked
diagnostic transfers. An event enumeration in a schema does not establish an
implemented unsolicited publisher.

The reference image binds this application service to TCP port 40001 [R5].
The service accepts a configurable bind endpoint, so examples using another
port do not define a second production service. The installed manifest shall
record the actual address, port, interface binding, server build, envelope
version and Protobuf schema revision.

Configuration requests, on-demand reads and large diagnostic transfers share
the same service and transport. Chunked replies remain traffic caused by a
request. A background device-reading thread does not make the network endpoint
a push stream. Any new unsolicited publication endpoint shall have an explicit
transport, socket pattern, activation rule and delivery contract.

The client contract shall define maximum request/reply size, chunk completion,
timeout, connection recovery, queue depth and handling of malformed,
unsupported or mismatched replies. The inspected server can discard malformed
or incompatible envelopes; clients therefore need bounded timeout behavior.
TCP delivery and a parsed envelope do not prove that a requested hardware
operation succeeded. Source code and configuration references shall identify
the authentication or network-access controls actually applied to this
board-facing connection.

\subsection{Hermes: IPBus over UDP}

The board-side \code{hermes_udp_srv} receives IPBus transactions over UDP.
The reference implementation listens on UDP port 50001, transfers requests
through the local hardware bridge and returns replies to the requesting
client [R6]. Its hardware bridge wait interval and timeout are implementation
settings, not a guaranteed end-to-end network response time.

The separate DAQ Hermes client continues to configure the readout-link
hardware through this interface. Hermes traffic does not pass through the
OPC UA server. The two board services share Ethernet, IP connectivity, the
board host and the admitted gateware image, while retaining separate sockets
and application protocols. The configured readout packets leave on the DAQ
data links; they are not the UDP/IPBus control packets.

The Hermes release shall identify the IPBus wire version, client library,
address-table revision, hardware bridge revision and transaction limits.
Transaction matching, ordering, retry behavior and timeout handling shall be
defined by that release. The mere presence of UDP does not provide reliable
delivery or permission to replay writes. Operations using a shared hardware
selector shall serialize the complete selection/transaction sequence at its
owning service.

The reference Linux image starts both services within a coordinated gateware
lifecycle [R5]. Keeping Hermes outside OPC UA does not remove this dependency.
Reconfiguration of the common gateware or loss of the shared Ethernet link
can affect both protocols. The server and DAQ integration shall account for
this when admitting concurrent operations.

\subsection{Timing exchanges}

Timing has two distinct communication paths relevant to this interface.
Supported local configuration requests reach the DAPHNE service over the
shared CCM connection and execute through local board drivers or mapped
register access. These requests belong in the integrated DAQ configuration
path when they are part of that configuration contract.

The DTS serial signal and optical endpoint-control exchanges use the timing
interface specified by DAQ--PDS and the DTS documents [R1, R2, R9]. They are
not Ethernet packets on the 1\,Gb CCM link. The timing master's management
interface is also a distinct endpoint. Its deployment protocol and the
endpoint-facing API shall be identified by Timing/DAQ; no route through
Hermes or the OPC UA server is implied merely by the word \emph{timing}.

The local PS interface is not a general tunnel to the endpoint's optical
control register space. The selected image and timing-controller release
shall document which operations are local, which are master-initiated, and
which replies complete each operation. This prevents an implementation from
sending a request to an unrelated service or assuming that one reachable
socket establishes the whole timing path.

\subsection{DAQ operational publication (opmon)}

Opmon is the DAQ operational-publication interface. The library defines a
publication API and selects an output through its configured backend; its
reference documentation includes file and standard-output backends [R7].
Consequently, \emph{opmon} alone does not identify a board port, a network
protocol or a broker. The deployed DAQ release shall specify the backend,
wire encoding, destination and delivery behavior actually used.

The inspected DAPHNE DAQ controller demonstrates two separate operations:
it makes application requests to obtain board data and then publishes through
opmon [R3]. The first operation consumes shared board CCM resources; the
second follows the configured DAQ publication path. Periodic publication
does not mean that the underlying board service provides unsolicited network
messages. The controller lifecycle and output activation shall be specified,
including behavior before configuration, after teardown and after a lost
connection.

With DAQ configuration moved into the OPC UA server, the integration shall
identify where any board-reading component executes and how DAQ publication
connects to it. Existing direct board polling shall be reviewed as part of
this change. This draft does not define opmon as an SC ingress path or require
SC communication to pass through a DAQ publication backend. The protocol
placement must be agreed before assigning additional board clients.

\subsection{Supporting protocols and local execution}
\label{sec:auxiliary}

The board service terminates a network request and executes it using internal
interfaces. AXI/MMIO, local IPBus bridging, I2C and SPI shall be identified in
the implementation's dependency description. Local driver calls, shared
memory or service-manager operations do not create additional Ethernet
connections. A new process-to-process API shall be documented separately if
the image introduces one.

The deployment protocol inventory shall also cover the following classes
\emph{where enabled}. Their presence or absence shall be explicit; this list
does not assert that every service is installed.

\subsection{Related PDS and DPS protocol boundaries}
\label{sec:related}

PoF laser control, LCMs, WIENER power supplies and DPS connections terminate
on their respective devices. The physical CCM description
copied above also covers an LCM link, but does not establish that the LCM
implements the DAPHNE Protobuf schema.

For WIENER equipment, the interface uses an SNMP agent at the
equipment and a driver that exposes an interface to Ignition. The installed
SNMP version, MIB revision, driver and actual OPC interface shall be recorded.
An SNMP-to-OPC translation is distinct from the DAPHNE Protobuf-to-OPC UA path.
For PoF/PLC and LCM equipment, the selected device API, client, protocol
version and endpoint remain to be supplied by their owners.

DPS integration requires its own controller/network interface description and
physical I/O contract. OPC UA may present a controller interface if that is
the selected implementation; this does not establish a protection path
through DAPHNE Ethernet. No DPS wire protocol, PLC endpoint or discrete-I/O
electrical specification is supplied by the board CCM description. Those
interface details shall be supplied by the DPS interface owner.

\subsection{Shared connection, contention and failure behavior}
\label{sec:contention}

The traffic budget shall include simultaneous OPC-UA-server-to-DAPHNE
transactions, Hermes transactions, any periodic board polling, diagnostics
and enabled maintenance traffic. OPC UA client traffic and DAQ publication
traffic must additionally be budgeted at the external host and switch ports
where they actually flow. A software component integrated into a physical
server still consumes CPU time, socket queues and network capacity.

Each service shall specify maximum message or transfer size, sustained and
burst traffic, concurrent requests, queue limits, timeout and retry limits,
and any allowed bulk-transfer window. The combined qualification shall use
the actual host and switch topology and the 42-board FD-VD scale. Nominal
1\,Gb Ethernet capacity alone cannot establish acceptable command latency.

The integration test shall exercise DAPHNE configuration while Hermes is
active, periodic work while a bounded diagnostic transfer runs, a slow or
disconnected client, and recovery after network or server restart. Evidence
shall distinguish link contention, server dispatch delay and local hardware
execution. An unresponsive service shall not be described simply as
\emph{Ethernet unavailable} when the other service still exchanges traffic.
Shared-image restart behavior shall be tested as well as socket reconnection.

\subsection{Online specifications, revisions and completion items}

Every protocol implementation in this interface shall have an online,
versioned specification accessible to its implementers. The release package
shall identify the physical-interface document, server and client releases,
Protobuf schemas, OPC UA model and methods, Hermes/IPBus/address-table
revisions, selected DAQ/opmon backend, timing API, and enabled infrastructure
protocols. Source and binary versions shall be tied together by immutable
revision identifiers or artifact hashes. A moving branch name alone is not a
reproducible interface version.
